# 微信机器人开发准备说明

> 文档日期：2026-09-15  
> 文档性质：设计准备，不代表机器人已经上线  
> 共享后端：`E:\nsh\nshls\RuoYi-Vue3-FastAPI-miniapp-backend\ruoyi-fastapi-backend`  
> 协议方向：暂定接入微信 iLink 类协议／网关，最终以实际可用协议和合规要求为准

## 1. 建设目标

微信机器人是网页和小程序之外的第三个使用入口。它不建立第三套活动数据，而是通过统一后端读取和操作现有业务。

三端最终关系：

```text
网页端：复杂管理、创建约战、拖拽排表、保存快照、导入战报
小程序：移动查看、报名、请假、个人资料、战报分析
微信机器人：消息查询、职业缺口提醒、链接分发、轻量本人操作
                         │
                         ▼
                 统一 FastAPI 后端
                         │
                         ▼
          账号、组织、活动、阵容、报名、战报数据库
```

机器人开发必须遵守：

- 不复制网页或小程序的活动数据。
- 不直接修改数据库，所有业务操作必须经过后端服务和权限校验。
- 不根据昵称猜测登录账号。
- 不根据活动名字或日期猜测战报归属。
- 不让机器人绕过“约战只能在网页约战排表创建”的当前规则。
- 不在群聊中泄露微信号、密码、房间密码或其他私人信息。

- 个人玩家资料。

- 修订号并发校验和操作标识防重复提交。

### 2.2 尚未完成

- 微信协议连接器。
- 微信账号与系统账号绑定。
- 机器人会话状态。
- 主动消息订阅和通知队列。
- 机器人命令解析。

- 机器人运行监控、告警和审计页面。

因此，当前状态应描述为“后端业务基础已具备，微信接入层尚未开发”。

## 4. 微信界面对应功能

机器人没有传统页面，但每个“对话场景”相当于一个界面。

### 4.1 首次使用／绑定场景

用户发送：

```text
绑定账号
```

机器人回复内容应包括：

- 当前尚未绑定时的说明。
- 一次性绑定链接或二维码。
- 链接有效期。
- 明确提示不要在聊天中发送系统密码。

推荐绑定流程：

```text
用户在微信中请求绑定
    ↓
机器人创建一次性绑定票据
    ↓
用户打开 HTTPS 网页或小程序
    ↓
用户在受控登录界面完成账号认证
    ↓
后端把微信主体 ID 与系统 account_id 绑定
    ↓
票据立即失效
    ↓
机器人回复绑定成功
```

禁止用户直接在群聊或私聊中把账号密码发给机器人。

### 4.2 查询公开活动场景

用户可以发送：

```text
公开约战
找约战
最近有什么活动
```

机器人回复每个活动的摘要：

- 活动名称。
- 发起帮会或俱乐部。
- 约战时间。
- 已安排人数、总席位和空位。
- 主要职业缺口。
- 小程序活动详情入口。

列表较多时只回复前几项，再提供“小程序查看全部”，避免群聊刷屏。

### 4.3 按职业查询缺口

示例：

```text
找缺素问的约战
铁衣有位置吗
查询沧澜活动
```

机器人处理：

1. 识别职业名称和别名。
2. 调用公开活动列表，使用职业条件筛选。
3. 只返回仍开放且存在对应职业空位的活动。
4. 返回活动数量、最近时间和缺口人数。
5. 附带小程序链接。

职业名称必须来自后端启用职业字典，不在机器人代码中长期维护另一份列表。

### 4.4 查询我的约战

用户发送：

```text
我的约战
我的帮会活动
我的俱乐部活动
```

前置条件：微信身份已经绑定系统账号。

回复内容：

- 当前账号所属帮会活动。
- 当前账号所属俱乐部活动。
- 时间、活动状态和空位。
- 本人是否已经占位。
- 小程序详情入口。

未绑定时只引导绑定，不允许用微信昵称模糊匹配账号。

### 4.5 查询指定活动详情

用户点击活动卡片或回复活动序号后，机器人可展示：

- 活动名称和组织。
- 约战时间。
- 公开／组织内部／已结束状态。
- 最新成功阵容快照版本。
- 团队、小队和位置摘要。
- 职业缺口。
- 是否存在战报。
- 小程序完整详情入口。

机器人只读取已保存快照，不读取网页管理员的浏览器本地草稿。

### 4.6 报名场景

第一版推荐机器人只负责引导，不直接代替用户完成选位置：

```text
用户：报名活动 2
机器人：请打开小程序，在活动详情选择空位和本人绑定角色。
```

这样可以让用户在小程序中清楚看到：

- 当前空位。
- 指定职业。
- 本人有效绑定角色。
- 并发后的最新阵容。

后续如果要在机器人内直接报名，必须同时提供：

- 明确活动 ID。
- 明确小队 ID 和位置编号。
- 明确本人绑定成员 ID。
- 当前活动修订号。
- 唯一操作标识。
- 二次确认。

任何一项不明确都不能自动报名。

### 4.7 请假／离位场景

第一版同样推荐跳转小程序完成。

后续机器人直办流程必须：

1. 查询本人在该活动占用的所有位置。
2. 若有多个位置，让用户明确选择。
3. 显示活动、玩家和位置进行二次确认。
4. 使用修订号与操作标识提交。
5. 成功后返回最新阵容结果。

### 4.8 补人提醒订阅

个人中心未来增加“是否接受补人消息”开关后，机器人可提供：

```text
开启补人提醒
关闭补人提醒
提醒设置
```

默认订阅职业来源：

- 主职业。
- 用户明确允许时可同时订阅副职。
- 用户可单独选择某些职业。

触发条件：

- 新活动公开发布。
- 公开活动新增相应职业空位。
- 管理员发布格式化补人信息。

通知内容：

- 活动名称和时间。
- 缺少职业及人数。
- 发起组织。
- 小程序链接。

通知限制：

- 用户必须主动订阅。
- 支持随时关闭。
- 同一活动同一版本不得重复推送。
- 夜间免打扰和频率上限可配置。
- 位置已满后不得继续发送过期提醒。

### 4.9 管理员查询职业缺口

管理员或助手可以发送：

```text
查询本周四约战缺口
活动 123 还缺什么职业
```

机器人返回：

- 最新已保存快照版本。
- 总空位数。
- 每个职业缺少人数。
- 不限职业空位。
- 临时替补数量。
- 网页排表入口。

机器人不能读取尚未保存的本地草稿，因此回复中必须说明数据来自哪一次后端快照。

### 4.10 创建约战

当前统一业务规则是：新约战只能在网页“约战排表”创建。

因此第一版机器人收到：

```text
创建约战
周四开一个活动
```

应回复网页“约战排表”的入口和说明，不直接调用创建接口。

这样可以确保创建后立即配置团队、小队、六个位置和指定职业，避免机器人创建出无人配置、无法使用的空活动。

如果未来确实要开放机器人创建，必须先重新评审该业务规则，并要求管理者在创建后完成排表确认。

### 4.11 战报查询

用户可以发送：

```text
最近战报
活动 123 战报
我的历史战报
```

机器人回复：

- 活动名称和时间。
- 战报是否存在。
- 简短结果摘要。
- 小程序或网页完整分析入口。

战报只允许读取明确关联活动的数据。旧未关联战报已经清理，不恢复“按名称或日期自动猜配”。

### 4.12 上传 CSV 战报

此能力建议放到第二阶段，并且只对活动管理员／助手开放。

推荐流程：

```text
管理员选择明确活动
    ↓
发送 CSV 文件
    ↓
机器人读取文件并做格式预检
    ↓
回复活动名称、文件人数和匹配报告
    ↓
管理员确认绑定
    ↓
后端通过活动专用导入接口保存
```

机器人不得：

- 自动选择“看起来最像”的活动。
- 把未确认文件写入正式战报。
- 接收超出大小限制的文件。
- 在群聊回显完整敏感 CSV。

## 6. 技术结构建议

```text
微信/iLink 网关
    │ 接收消息事件、发送消息
    ▼
Bot Adapter 协议适配层
    │ 统一成内部消息格式
    ▼
Bot Application 机器人应用层
    ├─ 身份绑定
    ├─ 命令／意图解析
    ├─ 会话状态
    ├─ 回复模板
    └─ 通知调度
    │
    ▼
Integration API /api/v1
    │
    ▼
现有 ActivityService、PlayerProfileService、组织与权限服务
```

### 6.1 协议适配层

职责：

- 连接暂定 iLink 网关。
- 接收私聊、群聊、文件和回调事件。
- 把不同协议字段转换为统一内部消息。
- 发送文本、卡片、小程序链接和失败提示。
- 隔离协议变化，业务服务不直接依赖 iLink 字段。

内部消息建议字段：

```json
{
  "eventId": "微信事件唯一标识",
  "conversationId": "会话标识",
  "conversationType": "private|group",
  "senderSubjectId": "不可逆或受保护的微信主体标识",
  "messageType": "text|file|event",
  "text": "消息内容",
  "file": null,
  "receivedAt": "时间"
}
```

### 6.2 机器人应用层

机器人应用层负责业务编排，不直接写活动表：

- 将微信主体映射到系统账号。
- 识别命令和必要参数。
- 调用统一后端服务。
- 对结果做适合微信的简短格式化。
- 对危险或有副作用操作执行二次确认。
- 记录审计信息和幂等结果。

### 6.3 后端接口层

机器人可以复用现有接口语义：

- `GET /api/v1/organizations`
- `GET /api/v1/activities`
- `GET /api/v1/activities/{activityId}`
- `POST /api/v1/activities/{activityId}/signup`
- `POST /api/v1/activities/{activityId}/leave`
- `GET /api/v1/activity-reports/{reportId}`
- `GET /api/v1/player-profile/me`
- `GET /api/v1/profession-styles`

但机器人服务不应保存普通用户 JWT。建议新增服务器到服务器的内部调用身份，后端根据已绑定 `account_id` 构造受控用户上下文，并保留完整审计。

## 7. 建议新增的最小数据模型

用户之前提出数据库表过多，因此机器人不应复制活动、阵容、成员和战报表。只新增机器人自身必须的数据。

### 7.1 微信账号绑定表

`bot_account_binding`

- `id`
- `provider`：例如 `ilink`
- `subject_hash`：受保护的微信主体标识
- `account_id`：现有系统账号 ID
- `status`
- `bound_at`
- `revoked_at`
- 唯一约束：`provider + subject_hash`

### 7.2 通知订阅表

`bot_notification_subscription`

- `id`
- `account_id`
- 是否开启补人提醒
- 订阅职业集合
- 是否使用主职业／副职
- 免打扰时间
- 更新时间

一个账号一条配置即可，不为每个职业建立大量重复行。

### 7.3 会话与一次性票据表

短期会话优先放 Redis：

- 当前选择的活动。
- 等待用户确认的报名／请假。
- 一次性绑定票据。
- CSV 上传预览。

只有必须审计的最终结果才写数据库，避免产生大量无用会话表。

### 7.4 消息审计与发件箱

可以使用一张精简的 `bot_message_job` 表同时记录主动通知任务和最终状态：

- 业务事件键。
- 接收账号。
- 消息类型。
- 脱敏后的摘要。
- 状态、重试次数和下次重试时间。
- 协议消息 ID。
- 创建和发送时间。

唯一约束防止同一活动同一版本向同一账号重复发送。

## 8. 身份、权限和隐私

### 8.1 身份绑定

- 微信昵称、群昵称和头像不能作为账号身份。
- 必须通过一次性票据和系统登录完成绑定。
- 一个微信主体绑定一个有效系统账号。
- 解绑后立即停止私人查询和通知。
- 管理权限每次从后端实时读取，不缓存在机器人永久配置里。

### 8.2 群聊规则

群聊可以回复：

- 公开活动。
- 公开职业缺口。
- 不包含隐私的活动摘要。

群聊禁止回复：

- 用户微信号。
- 其他成员私人资料。
- 组织内部活动详情。
- 房间密码等敏感信息。
- 完整 CSV 数据。

私人结果应提示用户转私聊或打开小程序。

### 8.3 管理权限

- 管理员和助手身份必须来自真实组织关系。
- 平台管理员不应自动获得所有帮会私人信息。
- 机器人不能接受“我是管理员”文字作为授权。
- 文件上传、活动变更等操作必须记录操作账号和组织。

### 8.4 日志脱敏

日志不得记录：

- 明文密码。
- 完整 JWT。
- 完整微信号。
- 原始微信主体 ID。
- 房间密码。
- 完整用户 CSV 内容。

## 9. 消息解析策略

第一版优先使用明确命令和有限自然语言，不急于引入复杂大模型：

```text
帮助
绑定账号
解绑账号
我的约战
公开约战
找缺素问的约战
活动 123
最近战报
开启补人提醒
关闭补人提醒
提醒设置
```

解析顺序：

1. 精确命令。
2. 职业词典和固定句式。
3. 当前会话上下文中的序号选择。
4. 无法确定时追问，不猜测活动或用户。

大模型未来只负责理解表达和生成自然回复，权限、数据查询和写操作仍由确定性代码控制。

## 10. 主动通知流程

推荐使用后端业务事件加发件箱：

```text
管理员发布公开活动／保存出新职业缺口
    ↓
后端产生业务事件
    ↓
通知服务查找已订阅且职业匹配的账号
    ↓
写入去重后的消息任务
    ↓
机器人发送微信消息
    ↓
记录成功或按退避规则重试
```

不能通过每隔几秒扫描整张活动表来判断是否需要通知，否则容易重复推送且浪费数据库资源。

## 11. 错误处理

| 场景 | 机器人回复 |
| --- | --- |
| 未绑定账号 | 引导使用一次性绑定链接 |
| 账号已禁用 | 提示到网页联系管理员，不泄露内部原因 |
| 无组织权限 | 明确说明无权查看该组织活动 |
| 活动不存在 | 提示活动已删除或链接失效 |
| 活动版本冲突 | 提示阵容已变化，返回最新小程序入口 |
| 位置已满 | 提示重新选择位置 |
| 职业不符合 | 显示该位置要求和本人职业 |
| 协议发送失败 | 后台重试，不重复执行业务写操作 |
| 后端不可用 | 说明服务暂不可用，不返回假结果 |
| 无法理解命令 | 返回简短帮助菜单 |

## 12. 开发阶段建议

### 第一阶段：只读机器人

- 完成协议连接。
- 完成安全绑定。
- 查询公开活动。
- 按职业查询缺口。
- 查询我的约战。
- 查询活动详情和战报摘要。
- 返回小程序链接。

### 第二阶段：通知机器人

- 增加补人提醒开关。
- 职业订阅。
- 活动发布事件。
- 去重、限流、免打扰和失败重试。

### 第三阶段：轻量本人操作

- 报名和请假的二次确认流程。
- 幂等操作。
- 并发冲突后的最新状态提示。

### 第四阶段：管理辅助

- 管理员查询阵容缺口。
- 格式化发布补人信息。
- CSV 预检和明确活动绑定。
- 机器人管理和审计页面。

## 13. 测试计划

### 身份测试

- 未绑定用户不能查询私人活动。
- 绑定票据只能使用一次且会过期。
- 解绑后立即失效。
- 微信昵称变化不影响绑定。
- 切换系统账号不会串数据。

### 权限测试

- 普通成员不能执行管理操作。
- 助手只能管理所属组织。
- 组织外用户只能看到公开活动。
- 群聊不能泄露私人资料。
- 微信号不会进入公开消息和日志。

### 活动测试

- 机器人查询结果与网页、小程序一致。
- 未保存草稿不出现在机器人结果中。
- 发布公开后才可被公开查询。
- 活动结束后停止报名并进入历史。
- 职业缺口与最新快照一致。

### 并发和幂等测试

- 两人同时报名同一位置只有一人成功。
- 重复微信事件只执行一次。
- 发送失败重试不会再次报名或请假。
- 活动修订号变化时要求重新确认。

### 通知测试

- 仅向主动订阅用户发送。
- 职业匹配正确。
- 同一版本不重复通知。
- 满员后不再推送旧缺口。
- 关闭提醒后不再产生新任务。

## 14. 部署与运维

建议机器人进程与主 API 分离部署，但使用同一代码仓库和服务契约：

- 主 API 负责业务和权限。
- Bot Worker 负责协议连接和消息发送。
- Redis 保存短期会话、锁和队列状态。
- MySQL 只保存必要绑定、订阅和审计结果。
- 健康检查分别监控 API、协议连接和发送队列。

需要监控：

- 协议在线状态。
- 接收消息延迟。
- 后端接口错误率。
- 待发送任务数量。
- 发送成功率和重试次数。
- 重复事件拦截数量。
- 绑定失败和权限拒绝数量。

## 15. 开发前必须确认的问题

1. 最终使用的微信协议名称、版本和部署方式是否确认为 iLink。
2. 该协议是否支持私聊、群聊、文件、小程序卡片和主动消息。
3. 微信主体的稳定唯一标识是什么，如何安全保存。
4. 主动消息的频率、风控和合规限制是什么。
5. 绑定页面使用网页还是小程序承载。
6. 第一版是否只做查询和通知，不直接报名／请假。
7. 机器人是否只服务一个微信号，还是支持多机器人实例。
8. 群聊白名单和管理员维护方式。
9. 小程序链接或二维码生成所需的正式 AppID 和域名。
10. 生产环境的数据保留、日志脱敏和告警规则。

## 16. 第一版验收标准

- 微信用户可以安全绑定现有系统账号，聊天中不传密码。
- “我的约战”与网页和小程序结果一致。
- 可以按职业查询公开活动缺口。
- 回复包含准确时间、组织、空位和小程序入口。
- 未绑定和无权限用户不能获取私人活动。
- 不创建活动、不编辑排表、不绕过网页唯一创建入口。
- 机器人后端不可用时不返回缓存假数据。
- 所有消息事件具备去重能力。
- 私人字段和 Token 不进入日志。
- 关闭订阅后不再收到补人提醒。
