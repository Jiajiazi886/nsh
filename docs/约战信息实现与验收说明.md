# 约战信息实现与验收说明

实施分支：独立副本的 `xiaochengxu`。原毕业项目保持只读。

## 已实现功能

```text
帮会管理 ─ 约战信息 ─┐
                     ├─ 我的约战：PC 左帮会、右俱乐部；小程序顶部分类切换
个人管理 ─ 约战信息 ─┤─ 找约战：明确公开、职业需求、空位筛选
                     └─ 历史战报：组织历史 + 本人参战，保留未关联旧战报
                                 │
                             共用约战详情
                                 ├─ 组织阵容只读、六席小队、职业标记
                                 ├─ 公开活动本人绑定角色报名/请假
                                 ├─ 管理员/助手明确发布、结束、战报关联
                                 └─ 管理员/助手进入网页约战排表
```

网页约战排表：先选择/创建活动；紧凑竖排小队；团队和小队增删/改名；鼠标拖拽移动/交换玩家；点击职业树选择玩家，默认全部收起；设置每个位置的指定职业或不限；当前活动临时替补；历史快照加载到本地草稿。

保存改为新接口的一次事务，不再用旧接口逐个创建/删除/分配。每十秒只写 IndexedDB；明确点击保存才生成成员可见快照。失败保留旧可见快照与草稿，版本冲突不自动覆盖；网络不确定时复用已保存的操作标识重试。

普通成员的只读权限由后端执行，不依赖隐藏按钮。公开报名与排表编辑权限独立。组织外玩家可以使用其本人有效绑定角色报名，不要求属于活动发起帮会。职业不符、位置已占、重复占位、跨组织安排和冒用成员 ID 均拒绝。

保守默认：已公开报名的位置不能在排表中直接移出或移动，须报名者先请假；避免保存成功却又被报名记录还原。普通组织预排玩家仍可由管理员/助手配置。

现有系统没有俱乐部实体，因此新增最小俱乐部模型：管理账号创建俱乐部，所有者按已绑定成员 ID 授权成员/助手。助手权限只在该组织内有效，平台角色不能代替组织授权。

小程序主工程与原嵌套 demo 的活动页均已接入统一 SDK。嵌套 demo 的登录、账号和组织页使用真实接口。旧离线 CSV/分析盒子保留，明确与共享活动战报区分，不作为请求失败时的回退。

## 接口约定

统一账号 JWT、`/api/v1`、camelCase 请求/信封、字符串 ID。列表返回 `items/page/pageSize/total`。失败返回真实 HTTP 状态、`errorKey` 与 `requestId`，不返回异常细节。

| 接口 | 用途 |
|---|---|
| GET/POST `/api/v1/organizations` | 本人组织列表 / 创建组织 |
| POST `/api/v1/organizations/{orgId}/members` | 俱乐部所有者明确授权成员或助手 |
| GET `/api/v1/activity-profiles` | 本人绑定角色；带 orgId 时仅管理员/助手读取组织候选 |
| GET `/api/v1/activity-professions` | 启用的职业选项 |
| GET/POST `/api/v1/activities` | 列表 / 创建活动 |
| GET `/api/v1/activities/{id}` | 共用详情与当前只读阵容 |
| GET `/api/v1/activities/{id}/snapshots` | 组织成员读取历史快照 |
| PUT `/api/v1/activities/{id}/lineup` | 原子保存阵容快照 |
| POST `/api/v1/activities/{id}/publish`、`/end` | 公开发布 / 结束并冻结最终阵容 |
| POST `/api/v1/activities/{id}/signup`、`/leave` | 本人报名 / 请假 |
| POST `/api/v1/activities/{id}/reports` | 明确关联已有 CSV 战报 |
| GET `/api/v1/activity-reports`、`/{reportId}` | 历史战报列表 / 安全游戏数据详情 |

活动列表参数：`kind=mine/public/history`、`page`、`pageSize`；可用 `orgType=guild/club`、`profession`、`vacantOnly` 筛选。小程序组织切换先在服务端分类，再分页，避免另一类活动被第一页挤掉。

写入携带 `expectedRevision` 和 `operationKey`。同一活动、同一操作者、同一操作标识不能用于不同请求。快照版本沿用活动修订号，报名/发布等操作也会增加修订号，因此快照版本可以不连续。

活动时间使用无时区的本地 ISO 格式，例如 `2026-09-20T20:00:00`，与现有 DateTime 数据保持一致；部署服务器应使用 Asia/Shanghai。结束时间关闭公开报名；管理员明确结束后冻结阵容并进入历史。

既有帮会的组织来源为管理账号 ID；本人身份使用 `GuildMember.member_user_id`，不是玩家昵称，也不是成员记录的所属管理者 `user_id`。

战报必须明确关联；不猜测标题、日期。未导入/关联 CSV 显示“暂无战报数据”。游戏数值以字符串返回，防止 JavaScript 大整数精度损失；不暴露 CSV 原始文件路径、联系方式或账号绑定信息。

## 尚未执行的启用步骤

本次没有连接真实 MySQL/Redis，没有迁移现有 `ruoyi` 库，没有重启现有服务，没有部署发布，也没有接入机器人。

1. 先为独立副本准备独立测试数据库和 Redis，核对副本的 `.env.dev`。数据库必须是新测试库，例如 `nsh_activity_test`，不能直接照用旧 `ruoyi` 库。
2. 手动审阅并在测试库执行 `sql/20260914_activity_information_mysql.sql`；PostgreSQL 对应 `..._postgresql.sql`。这些文件不自动执行、不包含 `USE ruoyi`。
3. MySQL 菜单脚本为 `sql/20260914_activity_information_menus.sql`。执行前确认 `47000..47007` 未占用、guild/personal 父菜单存在。它仅授予约战阅读菜单与目录，不授予原排表编辑权限；仅用于首次安装，不可重复直接执行。
4. 在独立副本环境中设置 `NSH_ACTIVITIES_ENABLED=true`，再由你启动/重启测试后端。默认是 false，新活动表已排除在现有启动自动建表流程之外；原有启动逻辑仍可能初始化其他表，因此绝不能把测试启动指向旧数据库。
5. 网页环境设置 `VITE_APP_BASE_API=/dev-api`，开发代理指向该测试后端。当前小程序本地接口在 `config/env.js` 为 `http://127.0.0.1:9100`，应与测试后端地址一致。
6. 真机中 `127.0.0.1` 是手机自身，需要改为手机可访问的测试地址；正式发布须配置真实 HTTPS API 根地址及小程序合法域名。不能未经部署就使用旧生产域名验证新接口。
7. 启用后用 `/api/v1/capabilities` 确认 `activityInformation/activitySnapshots=true`。旧运行进程未重启时不会自动加载此次源码。

未启用时返回明确 503；错误表结构返回服务异常，不会切换为假活动。
