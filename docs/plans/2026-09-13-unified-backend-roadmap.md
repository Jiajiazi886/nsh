## 1. 当前交付边界

本次完成第三/第四步：基于现有源码拟定多端统一后端设计、接口和后续开发顺序，在独立副本的 xiaochengxu 分支提交文档。

未实施运行代码、数据迁移、前端对接或真实机器人。本文件的“验收通过条件”是未来开发应满足的条件，**不是本次已经跑过的后端测试结果**。

## 2. 开发顺序

### P0：安全隔离、统一账号和组织范围

1. 保持原项目不动，继续在独立副本开发；Git origin 使用原 GitHub 地址，不指向本地原仓库进行推送。
2. 使用新的虚拟环境、独立 MySQL/Redis 测试实例和专用上传目录，不复制原 .env/凭证，不启动原项目。
3. 测试入口拒绝非测试数据库：名称/主机 allowlist + 显式测试标记 + 独立凭证；不能单靠数据库名包含 test 或“记得不要连生产”。
4. 检查已有 startup/schema 自动写库行为；测试禁用任务/自动初始化，使用可控迁移 fixture。
5. 复用登录、验证码、JWT 和 Redis session；补 PC/小程序同时登录、分别登出的验证。
6. 增加组织映射和 OrgScopeService；建立真实组织内的管理员/助理权限。
7. 增加不依赖帮会成员资格的本人玩家资料，保留 SysUser 密码/角色源。
8. 优先修正新服务及将迁移的旧明细查询的对象权限，验证跨账号/跨组织 ID 无法越权。

退出条件：同一账号多端登录成功；成员/助理都读到正确本帮会；系统权限与组织权限不混用；测试不能触达原库。

### P1：模板、活动和结构化预排

1. 新增模板、独立活动、团/队/六席位 live 结构；父子关系和稳定 ID 校验。
2. 新旧名单/模板 JSON 使用不同解析入口，全部预览后确认。
3. 将旧持久化排表结构转为模板预览，workbook 暂保留只读；不删除旧页面或表。
4. 增删改名/排序、选成员/移动/交换/清空统一命令，expectedVersion 防并发覆盖。
5. 席位可指定单职业或不限；职业不符先警告，管理例外必须确认/授权/原因。
6. 活动临时替补只写活动参与者，不进入永久 GuildMember 或下一活动。
7. 职业树统一 DTO，空职业/新增职业不消失，正文保持简单高对比界面。

退出条件：网页拖拽和小程序点击可使用相同命令测试；队永不超过六人；发布前普通玩家不能查看/安排；临时替补活动隔离。

### P2：多次快照、发布与公开抢位

1. 快照深复制结构和当时成员资料，保存 hash/schemaVersion/versionNo。
2. 恢复只产生新的编辑版本，禁止覆盖历史/公开报名/既有分析。
3. 发布快照 → releaseId + 公开 live 结构；公开查询不读取编辑稿。
4. 本人报名检查职业来自本人资料，不允许填任意职业或 userId。
5. 实现数据库锁/唯一约束/幂等收据；同席位/同用户多席位并发测试。
6. 截止时间服务端强校验，即使定时状态切换未运行也拒绝报名。
7. 最终快照从真实报名结果生成，必须包含发布后新报玩家和本场临时替补。
8. 公开后的编辑/撤销策略按确认结果实现，默认不启用破坏性重发布。

退出条件：多次快照不覆盖；仅管理员或明确授权角色发布；公开合职业抢位；十个请求抢同位只有一人成功；最终快照真实反映参战结果。

### P3：CSV、正式分析和分析盒子

1. 原文件进入受控存储，大小/内容/编码/引用字段/行数/固定表头/数字校验。
2. 以固定 fixture 回归原 CSV 的两帮会结构；不要依赖原微信文件路径作为 CI 唯一测试输入。
3. 同一 CSV 对最终快照名/alias 匹配，多帮会评分与零匹配警告。
4. 队伍 JSON、CSV 两种导入顺序不破坏独立数据；活动名单必须做成员权限校验。
5. 服务端预览绑定 hash/快照/组织/规则/有效期，确认后事务写 records 和 run。
6. 正式分析要求活动结束和最终快照；无上下文文件进入待处理。
7. 指标 ID 适配旧 battle_record，精确整数序列化、汇总和排序。
8. 分析盒子按小队基选 + 玩家增减去重；CSV 独有玩家可加入盒子，不入永久成员。
9. 多次上传/重新绑定生成新 import/run，旧结果/盒子保留，失败时不污染旧数据。

退出条件：目标 fixture 两个 60 人帮会可识别，九肆最终 roster 60 人时匹配 60/60；全部 12 个稳定指标有值/可汇总；异常报告正确；失败不覆盖旧 run。

### P4：机器人查询、绑定和可靠通知

1. 先实现 fake transport 与业务层工具测试，不接真实用户。
2. 短期一次性挑战、入站来源验证、绑定/解绑、幂等与限流。
3. 公开活动数量/指定职业缺口/本人可报/本帮会人数查询共用业务 Service。
4. outbox 事务写入、职业偏好筛选、重试/退避/去重/死信、解绑后阻止发送。
5. 对房间密码/私人活动信息做输出范围和日志脱敏。
6. 实际验证 iLink 的身份、消息上下文、主动发送、文件和入口能力；通过前保持关闭。
7. CSV 接收只推荐同权限活动并询问确认，未确认进入待处理。
8. MCP/知识库后置：查询白名单、组织/用户过滤、最小权限和写确认，不向 AI 暴露数据库。

退出条件：假通道证明业务正确、重复消息不重复变更、通知不误发/重复发、私有查询不能越权。真实通道还需另一次选型和试运行验收，不把 mock 通过当成微信实测通过。

### P5：多端集成与兼容验收

1. 网页新增 API adapter 和结构化阵容页，原排表/history/workbook 保留。
2. 小程序用新请求/上传封装逐页替换假 store，不再分别存正式排表/报名/分析。
3. 两端相同 activityId/releaseId/runId、移动/报名后跨端刷新一致。
4. 小程序配色维持白/灰/蓝 + 职业小色块，所有候选/玩家列表职业树展示，不引入华丽主题。
5. 用户自行在开发者工具/真机反馈，本代理不操作其电脑界面。
6. 验证旧网页已存在账号/成员/审核/记录读取无破坏，前端错误响应兼容。

退出条件：用户按完整赛前→公开报名→赛后分析流程验收；不仅是后端 unit test 绿色。

## 3. 数据迁移与回退

| 步骤 | 做法 | 必须保留的保护 |
| --- | --- | --- |
| 0：离线预览 | 读取旧 owner/成员/排表/邀请/比赛关系 | 不向原数据库写入，脱敏样本 |
| 1：组织映射 | 确认 owner → orgId，异常单独列出 | 硬编码 guildId=1 不自动扩散归属 |
| 2：新表增量 | 用受审查显式迁移建新结构 | 不 DROP/TRUNCATE 旧表，两个 dialect 按实际支持验证 |
| 3：结构转换 | 旧团/队/assignment → 模板/活动预览 | workbook 不可解释部分人工处理，不能假装自动迁移成功 |
| 4：历史分析关联 | 旧数据保持 legacy 来源 | 没有最终快照的历史记录不能捏造“正式 finalSnapshot” |
| 5：灰度读取 | 特性开关仅给测试组织开放 | 旧 API 和菜单继续可用，部署不自动迁移所有组织 |
| 6：逐步写入 | 新活动使用新模型；旧活动只读历史 | 不同时开放两套独立编辑造成双主状态 |
| 7：回退 | 关闭新入口/通道/worker，恢复旧读取 | 新表/文件保留取证，不逆向覆盖原历史或删除比赛 |

正式迁移前需要独立备份、恢复演练、数据数量/归属对账。数据库迁移与代码回退不是一回事，不能用 git checkout 代替数据库恢复。

| 展示他人姓名 | 暂拟公开仅脱敏名字/职业/状态，联系方式不公开 | DTO 投影 |

| 同人多席位例外 | 第一版禁用 | 唯一约束 |

| 俱乐部/80/800 人限制、60/120 规模 | 保留扩展字段，正式容量规则另定 | 组织模型/入口 |
| 创建码/邀请码 | 不复用特殊昵称权限；期限与审核另定 | 新组织管理 |
| 一次延期/1..120 分钟 | 待确认，不绑定活动 endTime 作为报名截止 | 时间/状态 |
| 用户推送 | 只 opt-in、按职业、通道支持才发送 | 偏好/合规/重试 |
| iLink 最终协议/运行方式 | 未启用，先 fake transport | 真实身份/消息能力 |
| CSV 重绑/换 final | 新 run 保留历史，需确认权限与界面 | 分析版本 |
